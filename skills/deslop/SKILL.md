# 한국어 AI 문체 제거

축이 넷이다. 위에서 아래로 본다.

| 축 | 무엇을 잡나 | 판정 질문 |
|---|---|---|
| **존재** | 있을 필요가 없는 줄·문단·섹션 | 이 줄을 읽고 독자의 행동이 바뀌나 |
| **이해** | 독자가 해독할 수 없는 문장·절 | 처음 받은 사람이 자기가 뭘 해야 하는지 아나 |
| **구조** | 문서·문단 골격의 습관 | 서론 선언, 양비론, 3항 나열, 불릿 의존 |
| **표현** | 어미·수식어·접속부사 | 단정 회피, 공허한 강조, `이를 통해` |

존재 축이 먼저다. 지울 문단의 어미를 고치는 것은 낭비고, 표현만 다듬으면 분량은 그대로 남는다.
그다음이 이해다. 독자가 못 읽는 문단을 골격에 맞춰 정렬해도 여전히 못 읽는다.

## 철칙 — 모든 규칙보다 우선

1. **지우되 만들지 마라.** 추상어를 구체어로 바꾸는 것은 원문에 그 구체가 있을 때만 한다. `다양한 요인`의 요인이 원문에 없으면 요인을 발명하지 말고 구절째 들어낸다. 숫자·사례·고유명사를 지어내는 순간 날조다.
2. **정보를 보존하라.** 사실·주장·논점·뉘앙스는 남긴다. 결과가 원문 절반 아래면 논점까지 지웠는지 되짚는다.
3. **레지스터를 깨지 마라.** 보고를 구어체로, 고객 카피를 메모로 바꾸면 문체가 무너진다.
4. **한 문체로 수렴하지 마라.** 모든 문장을 3어절 단정문으로 바꾸면 그것이 새 slop이다(`references/structures.md` 단일 문체 수렴).

## 레지스터 — 우리 표면

교정 전에 어느 표면인지 정한다. 판정 단위는 블록이다. 보고서에 인용된 고객 문의는 그 블록의 레지스터로 본다.

| 표면 | 신호 | **종결어미** | 교정 후에도 남아야 할 것 |
|---|---|---|---|
| 슬랙 대화형 | 부탁·안내, 수신자 호칭 | **~해요 · ~거든요** | 쉬운 말, 마커 없는 줄글, 청유형 |
| 슬랙 데이터공유형 | 숫자 3개 이상 | **~함 / ~다 / ~음** | `질문 : 답` 헤더, 개조식, 분자/분모 |
| 노션·문서 (팀이 읽는 것) | 제목 + 섹션 | **~입니다 / ~합니다** | 결론 먼저, 표, 액션 후보 표기 |
| PR 본문 | 리뷰어가 볼 판단 지점 | **~입니다 / ~합니다** | 결정축, 스키마·마이그레이션 경고 |
| 핸드오프 | 상황과 증거 분리, 요청 | **~입니다 / ~합니다** | 자립성, 실행 가능한 CTA |
| 아티팩트·덱 | 요지 카드, 토글 | **~입니다** (제목·라벨은 명사구) | 카드만 읽어도 완성되는 결론 |
| 고객 카피 | 존댓말, 컨시어지 톤 | **~입니다** | 정중한 어미, 브랜드 목소리 |
| 사용자에게 하는 보고 | `①한 것 ②검증 ③당신 차례 ④다음 차례` | **~입니다** | 표, 숫자, 4블록 골격 |
| 내부 실험문서·메모 | 나만 보거나 빠른 공유 | **음슴체(~음/~함/~임)** | 관찰형 담백 |

### 🔴 종결어미는 표면이 정한다 — 추측하지 않는다

**기본값은 `~입니다`다.** 팀이 읽는 문서(노션·PR·핸드오프·덱)는 전부 경어체다. 평서형 `~다`는 **개조식 불릿과 슬랙 데이터공유형에서만** 쓴다. 줄글 문단을 `~다`로 쓰면 팀 문서에서 즉시 교정 대상이다.

⚠️ **"평어"는 이 문서에서 "쉬운 말"이라는 뜻이다. 해라체(~다)가 아니다.** (2026-08-26 실사고: 이 두 뜻을 섞어 읽고 노션 팀 문서 전체를 `~다`로 썼다가 교정당했다.)

한 문서 안에서 종결어미를 섞지 않는다. 표 셀·이미지 캡션·제목은 명사구로 끝내도 된다.

**과장 형용사는 어느 표면에서도 slop이다.** 고객 카피에서도 `놀라운`, `완벽한`, `혁신적인`은 지운다.

## 0단계 — 존재 감사

문장을 고치기 전에 지울 것을 먼저 지운다. 한 줄씩 통과시킨다.

**이 줄을 읽고 독자의 행동이 바뀌나.** 안 바뀌면 지운다. 넣는 기준은 필요다.

기본으로 빼는 것 — 판단이 갈리면 뺀다. 판단이 갈린다는 것은 지웠을 때 잃는 정보가 있는지 확신이 없는 경우다.

| 지울 것 | 예 | 남기는 경우 |
|---|---|---|
| 작업 서사 | `먼저 A를 확인하고 B를 조회했습니다` | 없음. 물어본 사람에게만 |
| 검증 분량 자랑 | `테스트 12개 전부 통과` | 실패가 섞였을 때만 |
| 내부 식별자 | 함수명, 파일 경로, PR 번호, 컬럼명 | 그걸 열어볼 사람에게만 |
| 커버리지·정확도 수치 | `99.8퍼센트 일치` | 결론이 `된다/안 된다`가 아닐 때만 |
| 안 물어본 질문의 답 | 스레드 질문 2개에 섹션 5개 | 없음. 질문 수 = 섹션 수 |
| 유보·한계 문단 | `다만 표본이 작아 단정은 어렵습니다` | 없음. 결론 문장 안에 흡수한다 |
| 앞 문단을 표현만 바꿔 되풀이한 문단 | | 없음 |

질문에 답할 때의 기본형은 **답 한 줄과 근거 한 줄**이다. 근거를 셋 쓰고 싶으면 독자의 다음 행동을 바꾸는 하나만 남긴다.

**삭제 시험.** 목록에 없는 표현이 의심되면 지워보고 판정한다. 지웠을 때 잃는 정보가 없으면 slop이고, 잃으면 남긴다. 철칙 2가 우선한다.

## 0.5단계 — 말

**초등학생이 아는 낱말과 관습적으로 뜻이 분명한 낱말만 쓴다.** 여기서 걸리면 아래를 볼 필요가 없다. 못 읽는 글은 구조가 좋아도 못 읽는다.

낱말 하나마다 묻는다. **이 낱말을 처음 보는 사람이 사전 없이 아나.**

| 지울 것 | 예 | 대신 |
|---|---|---|
| **내가 지어낸 말** | `여기까지만 판다`, `볼 것 다섯 개`, `통으로` | 팀이 이미 쓰는 말을 찾아 쓴다. 없으면 사용자에게 묻는다 |
| **한자어 문어체** | `낭독`, `구술`, `조판`, `경계`, `편성`, `산출물`, `표찰` | `읽어주기`, `말로 답하기`, `범위`, `만든 것` |
| **업계 밖 영어** | `케이스`, `롤플레이`, `타겟` | `손님`, `역할 연습` |
| **줄임말** | `제안률`, `대면율` | `제안한 비율`, `얼굴 보고 만난 비율` |
| **뜻이 두 갈래인 짧은 말** | `있다`(무엇이 있다는 건지), `이걸`(무엇을) | 무엇을 가리키는지 낱말로 밝힌다 |

### 진짜 사람이 쓰는 말인가

지어낸 말은 짧고 그럴듯해서 알아채기 어렵다. **소리 내어 읽어보고, 실제 대화에서 이 문장을 들어본 적이 있는지 묻는다.**

| 안 쓰는 말 | 사람이 쓰는 말 |
|---|---|
| 세 번이 한 값입니다 | 세 번 오는데 가격은 한 번만 냅니다 |
| 같은 값 안의 순서입니다 | 2회차·3회차에 오염을 더 제거하는 일입니다 |
| 이 상태가 기본이 되게 합니다 | 지금 상태를 유지하려면 왁스와 보습이 필요합니다 |
| 날짜까지 말한다 | 다음에 언제 올지 함께 정한다 |

### 중간지대를 만들지 않는다 — 기술어를 쓰거나 쉬운 말을 쓰거나

**쉽게 쓰라는 규칙을 기술어 회피로 오해하면 제일 나쁜 말이 나온다.** 정확한 기술어를
피하려다 그 자리에 추상어를 놓으면, 개발자도 못 알아보고 비개발자도 못 알아보는 말이 된다.

독자가 그 기술어를 아는 사람이면 **기술어가 정답이다.** 모르는 사람이면 **동작으로 풀어쓴다.**
둘 중 하나를 고른다. 사이는 없다.

| 중간지대 | 기술어로 (독자가 개발자) | 쉬운 말로 (독자가 비개발자) |
|---|---|---|
| DB가 안쪽 값으로 질의하지 않는다 | 이 값들이 `WHERE`·`JOIN` 에 안 들어간다 | 이 값으로 찾아볼 일이 없다 |
| 질의·제약 대상만 컬럼이다 | `WHERE` 에 쓰거나 unique 를 거는 것만 컬럼이다 | 검색 조건이 되는 것만 따로 뺐다 |
| 이력이 불변이다 | 예약에 찍힌 값은 나중에 안 바뀐다 | 나중에 주소를 고쳐도 지난 기록은 그대로다 |
| 편성 SQL 재료 | 근무 편성 SQL 에 넣을 값 | 근무표를 만들 때 쓰는 값 |
| 배포가 걸려 있다 | 배포를 해야 한다 | 앱을 새로 올려야 한다 |

판정: **이 낱말을 다른 말로 바꿔 쓸 수 있으면 아직 확정된 말이 아니다.** `WHERE` 는 다른 말이
없다. `질의`는 있다.

🔴 **"쉬운 말로"는 동작을 풀어쓰는 것이지 이름을 갈아치우는 것이 아니다.** 토큰·티켓·영수증·크론·
푸시처럼 현장에서 실제로 부르는 이름은 비개발자 독자에게도 **그대로 쓰고 첫 등장에서 뜻을 한 조각
붙인다**(`토큰(앱이 폰마다 받아 서버에 맡기는 알림 수신용 문자열)`). "주소·배달원·쪽지·도장"처럼
번역어·비유어를 새로 만들면 독자는 그 말을 다시 실제 용어로 되번역해야 하고, 개발자와 대화할 때
통하지 않는다. 위 표의 "쉬운 말로" 열도 `WHERE`라는 이름을 숨긴 게 아니라 **그 절이 하는 일**을
쓴 것이다.

⚠️ 2026-09-15 실사고: eli5 아티팩트에서 `notification_token`을 "주소", Expo를 "배달원", `status='OK'`를
"도장"으로 바꿔 썼다가 "자꾸 주소라고 하는거냐, 토큰이라고 분명히 써. 이해를 위해 실제 많이 쓰는 용어를
안 쓰고 번역을 쓰면 그게 더 별로다"라는 지적을 받았다.

⚠️ 2026-08-27 실사고: 개발자에게 보내는 스키마 리뷰 글에 `DB가 안쪽 값으로 질의하지 않아서`
라고 썼다. `WHERE`·`JOIN` 이라고 쓰면 한 번에 끝나는 자리였다. "뭔 말임? 차라리 기술 언어를
쓰거나 아예 쉽게 하거나"라는 지적을 받았다.

### 우리 일을 「제거」로 부르지 않는다

같은 사실도 무엇을 없앤다고 쓰면 값이 깎이고, 무엇을 더한다고 쓰면 값이 선다. 우리는 오염을 없애는 사람이 아니라 차를 맡는 사람이다.

| 안 쓰는 말 | 쓰는 말 |
|---|---|
| 뺄 오염, 오염을 뺀다 | 케어할 오염, 오염을 케어한다 |
| 이 차에서 무엇을 뺄지 | 이 차에 어떤 가치를 더할지 |
| 겉, 안 | 외장, 실내 |

### 범위 밖이라고 자르지 않는다

우리가 못 하는 걸 손님이 말하면 부정하고 끝내지 말고, 우리가 가진 다른 것으로 잇는다. `그건 안 됩니다` 대신 `그건 이쪽 범위는 아닌데, 대신 이렇게 해 드릴까요`.

### 만든 사람만 아는 사정을 뺀다

문서를 만들면서 생긴 사정은 읽는 사람에게 아무 뜻이 없다.

- `종이에 쓰지 않습니다` — 왜 안 쓰는지 읽는 사람은 모른다
- `여기서 제일 많이 무너집니다` — 무너진 걸 본 사람만 안다
- `이 교본에서 제일 많이 펼칠 쪽` — 만든 사람의 예상이다

### 지시와 설명을 섞지 않는다

한 덩어리는 **읽는 것**이거나 **하는 것**이다. 둘을 섞으면 읽는 사람이 자기가 뭘 해야 하는지 모른다. 섞였으면 갈라서 각각 제목을 붙인다.

## 1단계 — 이해

남길 것을 정했으면 독자가 그것을 해독할 수 있는지 본다.
**판정 질문: 이 글만 처음 받은 사람이 자기가 뭘 해야 하는지 알 수 있나.**

1. **만든 사람 시점을 지워라.** 내부 구조 용어를 독자가 겪는 일로 바꾼다.
   `두 자리에서 걸림` → `답이 두 벌 보이고 아래쪽이 고친 것`. 모델은 맥락을 전부 들고 있어서 독자도 안다고 가정한다.
2. **메커니즘이 아니라 경험을 써라.** 무엇이 어떻게 도는지가 아니라 독자에게 무슨 일이 생기는지.
   헤더도 `어떻게 작동하나`가 아니라 `내 화면에서 뭐가 달라지나`로 세운다.
3. **처음 나오는 이름을 정의하라.** 스킬명·도구명·약어는 첫 등장에서 무엇인지 한 조각 붙인다. 정의를 피하려고 조어를 만들지는 않는다.
4. **예 하나가 설명 세 줄을 대체한다.** 판정 경계를 보여주는 실례를 넣는다. 없는 예를 지어내면 철칙 1 위반이다.
5. **전제를 세어라.** 독자가 모르면 문장이 무너지는 전제가 몇 개인가. 둘 이상이면 문장을 쪼개거나 전제를 본문에 넣는다.

표현 마커 0건, 골격 정상 — 다른 세 축은 전부 통과했다. 이 축이 없으면 안 잡힌다.

## 2단계 — 구조

긴 글은 구조부터 잡는다. 문단 단위로 지우거나 합친 다음에 표현으로 내려간다.

1. **서론을 선언하지 마라.** `이 글에서는 ~를 다루겠습니다`, `함께 살펴보겠습니다`를 지우고 첫 문장부터 본론.
2. **공허한 결론을 잘라라.** `앞으로도 관심이 필요합니다`, `기대됩니다`는 새 정보가 없다.
3. **이분법을 직접 서술로 풀어라.** `단순히 X가 아니라 Y` → `Y`.
4. **양비론을 끊어라.** `물론 ~한 측면도 있지만`은 결론을 흐린다. 반론에 무게가 있으면 정면으로, 없으면 삭제.
5. **3항 나열과 번호를 걷어라.** 순서가 결과를 바꿀 때만 번호를 쓴다.
6. **표·목록 예고 문장을 지워라.** `아래 표에 정리했습니다`는 표가 이미 하는 일이다.
7. **불릿에 의존하지 마라.** 판단이 필요한 내용을 불릿 셋으로 쪼개면 왜와 그래서가 증발한다. 메모·명세·절차는 면제.
8. **메타담화를 지워라.** `앞서 언급했듯이`, `정리하자면`.

상세와 나머지 패턴은 `references/structures.md`.

## 3단계 — 표현

1. **단정 회피 어미를 제거하라.** `~라고 할 수 있습니다` → `~입니다`. 불확실하면 무엇이 불확실한지 쓴다.
2. **공허한 강조어를 지워라.** `중요한 것은`, `핵심은`, `무엇보다도`, `본질적으로`.
3. **과장 형용사를 지우거나 수치로 바꿔라.** 근거가 원문에 없으면 삭제만 한다.
4. **접속부사를 단락당 1개 이하로.** `이를 통해`, `따라서`, `나아가`.
5. **사물을 주어로 쓰지 마라.** 데이터는 말하지 않는다. `쿼리해 보니 ~였다`처럼 사람이 주어다.
6. **막연한 권위에 기대지 마라.** `전문가들은`, `한 연구에 따르면`(출처 없이).
7. **AI 클리셰를 걷어라.** `의의가 있다`, `시사하는 바가 크다`, `패러다임`, `귀추가 주목된다`.

상세 목록은 `references/phrases.md`.

## 줄표와 기호 — 우리 규칙

- **줄표(—)는 우리 내부 문서의 실제 문체다.** 금지하지 않는다. 잡는 것은 여운·반전을 만드는 꺾기 하나뿐이다. `결국 남는 것은 하나 — 사람이다` → `결국 사람이 남는다`.
- `~`를 범위나 근사로 쓰지 않는다. 노션에서 취소선이 된다. 범위는 `-`, 근사는 `약`.
- `---` 가로줄과 이모지는 팀 공유글에서 쓰지 않는다.
- 슬랙에 보낼 글에는 마크다운 볼드·헤더를 넣지 않는다. 명령·URL은 코드블록에 넣는다.
- 영어 단어를 쓰지 않는다. 다만 영어를 피하려고 조어를 만드는 것이 더 나쁘다. 한국어로 안 되면 숫자나 동작으로 풀어 쓴다.

## 출력 전 게이트

교정 고유의 세 가지만 여기서 본다. 나머지 점검 항목은 `slop-audit` 스킬의 게이트 모드에 있고, 이 문서는 그것을 되풀이하지 않는다.

| 점검 | 걸리면 |
|---|---|
| 초등학생이 모를 낱말이나 내가 지어낸 말이 있다 | 바꾼다. 못 읽는 글은 실패다 |
| 원문·요청에 없는 사실·숫자·사례가 들어갔다 | 제거한다. 날조는 실패다 |
| 결과가 원문 절반 이하다 | 사라진 논점을 복원한다 |
| 레지스터가 바뀌었다 | 되돌린다 |

## 출력 형식

교정 모드는 **교정문 전문을 먼저**, 이어서 주요 변경 3-5개를 한 줄씩 쓴다. 전체 diff나 규칙 강의는 하지 않는다. 고칠 것이 거의 없으면 그렇다고 말하고 억지로 고치지 않는다. 판단이 갈리는 부분은 교정문 뒤에 묻는다.

생성 모드는 고치는 대신 애초에 쓰지 않는다. 쓰기 전에 표면과 목적을 정하고, 3항 나열·수사적 질문·`X가 아니라 Y`·사물 주어는 쓰려는 순간 멈춘다.
